**v5에서 바뀐 것 (10/13, 비판적 분석 후 확정)**
1. **핵심을 더 좁혔다.** "UI를 만드는 프로젝트"가 아니라 **"폰 안에서 캡처한 패킷으로 통화 품질을 추정하면 얼마나 맞는가, 틀리면 캡처 때문인가 모델 때문인가"를 검증하는 프로젝트**다.
2. **0–100 QoE 점수를 없애고 지표별 판정**(fps·bitrate·frame jitter·해상도마다 정상/주의/나쁨)으로 바꿨다. 점수 기준(예: 70점)에 근거가 없었기 때문이다. 판정 기준은 공개 자료에서 가져와 출처를 단다.
3. **라이브 손상 방식이 바뀌었다(Plan E).** 실측 결과 Clumsy는 **노트북 핫스팟을 지나는 폰 트래픽에는 안 걸린다.** 그래서 **노트북이 Meet 통화 상대**가 되고, 노트북이 보내는 영상에 손상을 건다. gnirehtet은 포기했다.

5. **방향 2(화면으로 정답 세기)는 하루만 써서 가능성부터 확인**한다.

## 1. 배경: vcaml은 무엇을 했나

### 1-1. 문제
영상통화 앱(Meet, 카카오톡 등)은 데이터를 **암호화**해서 보낸다. 그래서 통신사나 공유기 입장에서는 "지금 이 사람 통화 화질이 좋은지 나쁜지"를 직접 알 수 없다.

### 1-2. 택배 비유
인터넷 데이터는 **패킷(packet)** 이라는 작은 상자로 쪼개져서 오간다.

| 택배 | 인터넷 |
|---|---|
| 상자 | 패킷 |
| 송장(보내는 곳, 받는 곳, 무게) | **헤더(header)** — IP 주소, 포트, 길이 |
| 상자 안 내용물 | **페이로드(payload)** — 실제 영상·음성. 암호화돼서 못 본다 |

vcaml의 아이디어:
> 상자를 열지 않아도 **상자 크기와 도착 간격**만 보면 내용물을 짐작할 수 있다.
> 예: 큰 상자가 촘촘하게 많이 오면 → 고화질 영상이 잘 오고 있다. 상자가 띄엄띄엄 오면 → 화면이 끊기고 있을 가능성이 높다.

### 1-3. 어떻게 추정하나 (머신러닝)
1. 통화 중 패킷을 기록한다(= **pcap** 파일).
2. 1초 단위로 잘라서, 그 1초 동안 패킷 크기의 평균·최대·개수, 패킷 사이 간격의 평균·편차 같은 **통계값(feature, 특징)** 을 계산한다. vcaml에서는 이것을 `LSTATS`(크기 통계), `TSTATS`(간격 통계)라고 부른다.
3. 같은 1초 동안 브라우저가 기록한 **진짜 품질 값(정답)** 을 함께 놓고, **Random Forest**라는 머신러닝 모델에게 "이런 통계가 나오면 화면은 몇 fps였다"를 학습시킨다.
4. 학습된 모델에 새 통화의 통계만 넣으면 품질을 추정한다.

### 1-4. 무엇을 추정하나 (4가지 지표)
| 지표 | 뜻 | 단위 | 감 잡기 |
|---|---|---|---|
| **fps** (frame rate) | 1초에 화면이 몇 장 바뀌나 | frames/s | 30이면 부드럽고, 10 이하면 뚝뚝 끊김 |
| **bitrate** | 1초에 받는 데이터 양 | kbps (초당 킬로비트) | 높을수록 보통 화질이 좋다 |
| **frame jitter** | 화면 장면 사이 간격이 얼마나 들쭉날쭉한가 | ms (1/1000초) | 클수록 화면이 버벅인다 |
| **resolution** (frame height) | 화면 세로 해상도 | px (픽셀) | 720 = HD, 360 = 저화질 |

### 1-5. 논문 결과와 솔로 프로젝트 재현 [확인됨]
Sungmin이 솔로 프로젝트에서 vcaml을 Windows 노트북으로 재현했다(결과는 솔로 `docs/2. RUN_GUIDE.md`).

| 항목 | 논문 | 우리 재현 |
|---|---|---|
| fps 평균 오차 (IP/UDP 헤더만 쓴 ML) | 1.50 프레임 | **1.49 프레임** |
| fps 평균 오차 (RTP 헤더까지 쓴 ML) | 1.33 | 1.38 |
| 해상도 정확도 (Meet) | 97.74% | 97.75% |

→ "평균 1.5 프레임 정도만 틀린다"는 뜻이다. 화면이 실제로 30fps면 28.5~31.5 정도로 맞힌다.

### 1-6. vcaml의 한계 (= 우리 프로젝트의 출발점)
- **데스크톱 PC**에서 측정한 데이터만 있다(Meet, Teams, Webex). 모바일·카카오톡은 없다.
- **오프라인**: 통화가 끝난 뒤 파일로 한꺼번에 분석한다. 실시간이 아니다.
- 화면도, 사용자용 앱도 없다(연구용 코드).
- 논문에서도 실험실 데이터로 학습한 모델을 실제 가정 환경에 쓰면 Meet에서 오차가 크게 늘었다(솔로 노트 기준). → **환경이 바뀌면 정확도가 떨어질 수 있다.** 우리가 모바일에서 "얼마나 정확한가"를 검증해야 하는 이유다.

## 3. 전체 구조 (데이터가 흐르는 길)

```
 ┌──────────────── Galaxy S20 (Sungmin 폰) ────────────────┐
 │  카카오톡/Meet 영상통화  ←→  (상대: 팀원 iPhone)        │
 │        │                                                │
 │   PCAPdroid 앱: 폰이 주고받는 패킷을 기록(캡처)          │
 │        │                       ┌──────────────────────┐ │
 │        │                       │ 오버레이 버블 (Flutter)│ │
 │        │                       │ ● 나쁨  fps 12 (나쁨)  │ │
 │        │                       │ 원인: 패킷 손실        │ │
 │        │                       │ [조치] Wi-Fi 설정 열기 │ │
 │        │                       └──────────▲───────────┘ │
 └────────┼──────────────────────────────────┼─────────────┘
          │ 패킷 스트림 (USB 또는 Wi-Fi)       │ 결과 (WebSocket)
          ▼                                  │
 ┌──────────────── 노트북 (Windows) ──────────┼─────────────┐
 │  ① 1초씩 자르기 → ② 통계 계산(feature)                    │
 │  → ③ vcaml 모델로 fps·bitrate·jitter·해상도 추정           │
 │  → ④ 지표별 판정(정상/주의/나쁨) → 원인 표시 → 조치 문구     │
 │  → ⑤ WebSocket 서버가 1초마다 결과를 보냄 ─────┬──────────┘
 │                                                 ▼
 │                        React 웹 대시보드 (팀원 담당)
 │                        그래프, 정답 비교, What-if 슬라이더
 └──────────────────────────────────────────────────────────┘
```

**중요**: 모든 계산(추론)은 **노트북**에서 한다. 폰의 오버레이와 웹 대시보드는 **결과를 받아서 보여 주기만** 한다. 둘은 같은 형식의 메시지(`docs/SCHEMA.md`)를 받는다.

### 3-1. 단계별 설명
| 단계 | 하는 일 | 쓰는 것 |
|---|---|---|
| 캡처 | 폰의 패킷을 기록한다. PCAPdroid는 폰 안에 "가짜 VPN"을 만들어 모든 데이터가 그곳을 거치게 해서 기록한다(루팅 불필요) | PCAPdroid 앱 |
| 전송 | 기록한 패킷을 노트북으로 실시간으로 보낸다 | PCAPdroid의 TCP exporter(문서가 실시간용으로 권장) 또는 USB |
| 추정 | 1초 단위 통계를 계산해 vcaml 모델에 넣는다 | Python, vcaml, scikit-learn |
| 판정 | 4개 지표 각각을 정상/주의/나쁨으로 판정(하나라도 나쁨이면 전체 "나쁨") | `judge.py` (앞으로 작성) |
| 진단 | 품질이 나쁘면 원인을 추정한다: 대역폭 부족 / 패킷 손실이 중심 (지연·떨림, 약한 Wi-Fi는 보조) | `server/diagnosis.py` (규칙 기반, 구현됨) |
| 전달 | 1초마다 결과 메시지를 보낸다 | WebSocket (FastAPI) |
| 표시 | 폰에는 작은 버블, 노트북에는 분석 화면 | Flutter, React |

### 3-2. 지표별 판정이란 (v5: 0–100 점수를 대체)
**QoE(Quality of Experience)** = 사용자가 체감하는 품질. 처음에는 fps·bitrate·jitter·해상도를 합쳐 0–100점 하나로 만들려 했지만 **바꿨다.**
- 이유: ① "70점 이상이면 통과"의 70에 근거가 없다. ② 사람이 매긴 점수가 없어서 점수가 맞는지 확인할 방법이 없다. ③ 국제 표준 G.1070은 코덱·해상도별로 정해진 모델이라 우리 추정값을 넣어도 "표준을 따랐다"고 말할 수 없다("참고했다" 수준).
- 대신: 지표마다 **정상 / 주의 / 나쁨**을 판정한다. 기준값은 공개 자료(예: OpenTok 네트워크 테스트의 해상도별 bitrate·손실 표)에서 가져오고 출처를 적는다. 기준이 아직 정해지지 않았으므로 **지금은 "미정"** 이다.
- 주의: Zoom 등이 권장하는 "지터 40ms 이하"는 네트워크 지터이고, 우리의 frame jitter(화면 간격 편차)와는 다른 양이라 그대로 쓰지 않는다.

## 4. 세 가지 입력 모드

| 모드 | 무엇 | 언제 쓰나 | 비유 |
|---|---|---|---|
| **Live** | 지금 진행 중인 통화를 실시간 분석 | 데모의 핵심 | 생방송 |
| **Replay** | 미리 녹화한 pcap 파일을 실시간처럼 재생 | 개발, 그리고 데모 당일 Live가 실패할 때의 대안 | 녹화 방송 |
| **What-if** | 녹화된 실제 통화에 **가상으로** 손실·지연을 넣어 보고 품질 변화를 관찰 | 발표에서 슬라이더로 시연 | "만약 손실이 5%였다면?" 시뮬레이션 |

**What-if의 한계 (UI와 README에 반드시 적는다)**: 실제 앱은 네트워크가 나빠지면 스스로 화질을 낮춰 대응한다(**혼잡 제어**). 녹화된 기록은 이미 지나간 일이라 이런 반응이 없다. 그래서 What-if 결과는 "실제로 그렇게 됐을 것"이 아니라 "근사 시뮬레이션"이다.

## 5. 데모 계획 — 일부러 네트워크를 나쁘게 만들기 (v5: Plan E)

발표 때 "정상 통화 → 네트워크를 일부러 망가뜨림 → 폰 화면과 대시보드가 함께 나빠짐"을 보여 주려면 손상을 넣을 장치가 필요하다.

### 실측으로 알게 된 것 [확인됨, 10/13]
- 노트북 핫스팟으로 폰을 연결하는 구성 자체는 **잘 된다.** 집(5 GHz)에서 폰 직결 대비 다운로드 약 18% 감소, 지연 +3 ms 정도라 기준을 모두 넘었다. 학교(igc_user)는 아직 측정하지 않았다.
- 그런데 **Clumsy는 핫스팟을 지나가는 폰 트래픽을 건드리지 못했다.** Drop 10%를 걸어도 폰의 손실이 0%였다. 원인은 Windows 핫스팟의 주소 변환(NAT) 때문이다(WinDivert 문서도 같이 쓰지 말라고 경고). 반면 **노트북 자신의 트래픽에는 Clumsy가 정상 동작**했다.
- gnirehtet(USB 역테더링)은 USB가 수 초마다 끊겨 시험을 못 했고, PCAPdroid와 같이 쓸 수 없을 가능성도 있어 **포기**했다.

### Plan E (채택): 노트북이 통화 상대
```
 노트북(Meet 통화, 브라우저) ──[Clumsy: 손실·대역폭 제한]──→ 인터넷 ──→ 폰(Meet 통화)
                                                                    │ PCAPdroid가 캡처
 (핫스팟은 손상용이 아니라 "비교용 캡처"에만 사용)
```
- 노트북이 영상을 **보내는 쪽**이고, 그 길목(노트북 자신의 트래픽)에 Clumsy를 건다. 폰은 나빠진 영상을 받는다.
- 대역폭을 줄이면 보내는 앱이 실제로 화질을 낮춘다. What-if가 흉내 못 내는 **진짜 반응**이라 더 사실적이다.
- 폰 쪽은 지금까지 만든 PCAPdroid 캡처 그대로라 파이프라인을 바꿀 필요가 없다.
- **미확인**: 노트북 영상(가상 카메라 등)을 Meet에 내보내는 구성, Clumsy가 Meet 송신에 실제로 효과가 있는지, 카카오톡도 PC로 상대할 수 있는지. → **W1 파일럿에서 확인한다.**

### Plan C (예비): What-if 모드
Plan E가 안 되면 녹화 기록에 가상 손상을 넣는 What-if로 시연한다.

### 화면 배치
왼쪽에는 폰 화면(실제 통화와 그 위의 오버레이 버블), 오른쪽에는 웹 대시보드를 둔다. 폰 화면 미러링(scrcpy)은 USB 문제로 **보류** 중이라, 안 되면 폰을 카메라로 비추거나 화면 녹화로 대신한다.

## 6. "정확하다"를 어떻게 증명하나 (검증 실험 4가지)

이 프로젝트의 핵심 결과물이다.

### 실험 ① 캡처 충실도: "폰에서 기록한 데이터 자체가 정확한가?"
- PCAPdroid는 폰 안의 가짜 VPN에서 기록하므로, 실제 전파로 오간 패킷과 **시간·크기가 조금 다를 수 있다**.
- 방법: 같은 통화를 (a) 폰의 PCAPdroid와 (b) 노트북 핫스팟 쪽 Wireshark로 **동시에** 기록하고 비교한다. 패킷 수, 크기 분포, 간격 분포, 추정 결과를 본다.
- 결과: "차이가 ○○% 정도다"를 숫자로 보고한다.

### 실험 ② 정답 대비 정확도: "추정값이 진짜 값과 얼마나 가까운가?"
- **정답(ground truth)** 은 Chrome 브라우저의 **getStats**에서 얻는다. WebRTC 통화 중 브라우저가 실제 fps·bitrate 등을 알려 주는 기능이다.
  - 그래서 정답은 **폰 Chrome으로 하는 Meet 통화에서만** 얻을 수 있다.
  - 카카오톡은 정답을 볼 방법이 없다 → 결과에 항상 `validated: false`, "모델 추정값"으로 표시한다.
- 폰 Chrome에서 getStats를 1초마다 수집할 수 있는지는 **미확인**이다. M0에서 가능 여부부터 확인한다.
- 지표:
  - **MAE** (평균 절대 오차): 정답 30, 추정 28이면 오차 2. 이것들의 평균.
  - **±2 fps 정확도**: 오차가 2 이내인 초의 비율.
  - **Precision / Recall / F1 / Confusion Matrix**: "정상/저하" 판정이 맞았는지(설명은 11장).
- **일반화**: 데스크톱 데이터로 학습한 모델 vs 폰 Meet 데이터로 다시 학습(또는 보정)한 모델의 정확도를 비교한다.

### 실험 ③ 원인 진단 정확도 (v5: 범위 축소): "원인을 맞게 짚는가?"
Plan E에서 Clumsy로 **어떤 손상을 넣었는지 우리가 알고 있으므로**, 그것을 정답 라벨로 쓴다.

| Clumsy로 넣은 것 | 정답 라벨 |
|---|---|
| drop (패킷 버림) | `loss` (손실) |
| bandwidth (속도 제한) | `bandwidth` (대역폭 부족) |
| 아무것도 안 넣음 | `none` |

- 지표: 원인별 Precision·Recall, Confusion Matrix, 손상 시작부터 맞게 진단하기까지 걸린 시간(초).
- **고정 지연(lag)은 대상에서 뺐다.** 받는 쪽 패킷 간격이 변하지 않아 원리적으로 진단할 수 없다(합성 실험에서 97–100%가 "정상"으로 나옴). 지연·떨림(지터)과 **약한 Wi-Fi**(폰 RSSI)는 정성 확인만 한다.
- **손실은 RTP 순번**(패킷에 붙은 일련번호)이 보여야 잡힌다. IP/UDP만으로는 재현율이 0.03–0.18이다. Meet은 RTP가 보이고, 카카오톡은 미확인이다.
- 지금까지 숫자는 **데스크톱 기록에 소프트웨어로 손상을 합성한 시뮬레이션 결과**다(대역폭 재현율 0.95–1.00, 정확도 0.81–0.83). **폰 데이터는 아직 0건**이라, 발표에서 "폰에서 검증했다"고 말할 수 없다.

### 실험 ④ 앱 간 비교: Meet vs 카카오톡
같은 손상 조건에서 두 앱의 추정·진단 결과를 비교한다. 카카오톡은 정답이 없으므로 "정성 비교"로 표기한다.

### (선택) 방향 2: 화면으로 정답 세기 — 하루 파일럿
카카오톡에는 getStats 같은 정답이 없다. 대신 **노트북이 프레임마다 값이 바뀌는 영상을 보내고, 폰 화면을 녹화해서 실제로 몇 fps로 바뀌었는지 센다.** 먼저 Meet에서 getStats와 맞는지 확인하고, 맞으면 카카오톡에 적용한다. 하루 안에 ① 카카오톡 통화 화면이 녹화되는지 ② 녹화에서 프레임 변화를 셀 수 있는지 ③ Meet에서 getStats와 비슷한지 확인하고, 하나라도 막히면 접는다.

### 한계 (발표와 보고서에 그대로 적는다)
- 정답은 Meet에만 있고, 표본 수가 적다.
- What-if는 시뮬레이션이다.
- 진단 라벨은 인위적으로 만든 손상이다.
- 캡처 충실도와 모델 정확도는 **따로** 검증한다(섞으면 오차 원인을 구분할 수 없다). 루팅 기기가 없어 PCAPdroid 비루팅 모드 하나만 다룬다.
- PCAPdroid 캡처 방식이 측정에 영향을 줄 수 있다.

## 8. 팀 역할과 협업 방식

### 8-1. 역할
| 사람 | 담당 | 쓰는 컴퓨터 |
|---|---|---|
| **Sungmin** | Python·ML 서버(캡처 수신, 추정, 판정, 진단), Flutter 오버레이 앱(버블 UI 포함), 실험·분석 | Windows 노트북, Galaxy S20 |
| **팀원** | React 웹 대시보드(최소 범위), 필요 시 통화 상대 | Mac, iPhone |
| **함께** | 통화 실험 세션, 메시지 형식(SCHEMA) 합의, 발표 준비, 리허설 | |

### 8-2. 한 저장소(repo)에서 충돌 없이 일하는 법
- GitHub repo: `sungmin-c/cse310_MCQM` (public)
- **폴더 주인 정하기**: 자기 폴더만 고친다. 상대 폴더는 리뷰만 한다.
  ```
  cse310_MCQM/
  ├─ vcaml/        ← vcaml 원본 코드 (submodule, 아래 설명)      [Sungmin]
  ├─ server/       ← Python 서버                                [Sungmin]
  ├─ capture/      ← 캡처 수신 코드 (예정)                      [Sungmin]
  ├─ overlay/      ← Flutter 오버레이 앱 (예정)                 [Sungmin]
  ├─ tests/        ← Python 테스트                              [Sungmin]
  ├─ dashboard/    ← React 대시보드 (예정)                      [팀원]
  ├─ docs/         ← 명세, 일정, 메시지 형식, 이 문서          [공동]
  └─ data/         ← 데이터 (git에 안 올라감)                  [각자 PC]
  ```
- **브랜치 규칙**: `main`은 항상 실행 가능한 상태로 둔다. 작업은 `ml/주제`, `web/주제` 같은 브랜치에서 하고 PR로 합친다.
- **SCHEMA = 둘 사이의 계약서**: 서버가 보내는 메시지 모양을 `docs/SCHEMA.md`에 적고, 예시 6줄을 `docs/schema/sample.jsonl`에 둔다. 양쪽 테스트가 이 예시로 검사한다. 한쪽이 마음대로 바꾸면 테스트가 실패한다.
- **팀원이 서버 완성을 기다리지 않게**: 가짜 데이터를 1초마다 보내는 **더미 서버**가 이미 있다. 팀원은 Mac에 uv만 설치하면 된다.
  ```
  uv run server/dummy_stream.py      # → ws://localhost:8000/ws 로 1초마다 메시지
  ```
  [확인됨] 1.01초 간격으로 메시지가 오는 것을 확인했다.

### 8-3. vcaml 코드를 가져오는 방식 (fork + submodule)
- **fork**: 원본 vcaml을 내 GitHub 계정으로 복제한 것이다(`sungmin-c/vcaml`). 원본을 건드리지 않고 고칠 수 있다.
- **submodule**: 우리 repo 안에 vcaml 코드를 **복사하지 않고, "fork의 이 버전을 쓴다"는 링크만** 넣는 방식이다.
- 이렇게 한 이유: vcaml 원본에는 **LICENSE(사용 허가) 파일이 없다** [확인됨]. 라이선스가 없는 코드를 우리 public repo에 통째로 복사하면 재배포가 될 수 있어서 링크 방식을 택했다. 법률 판단은 아니다. **교수님께 확인할 사항**이다.
- 원본에서 바꾼 것: 설정 2줄뿐이다(데이터 폴더 위치, 다운로드 스크립트 경로 버그).

### 8-4. 데이터 재사용
솔로 프로젝트에서 받아 둔 데이터 약 15GB(실험실 2.2GB, 실사용 8.4GB, 학습 결과 4.2GB)를 **복사하지 않고 바로가기(junction)로 연결**했다. 솔로 자료는 읽기만 하고 수정하지 않는다. 수정되지 않았는지는 파일 지문(SHA256)으로 확인했다.

| 0–2분 | 문제: 앱 내부를 안 보고 모바일 통화 품질을 알 수 있을까? |
| 2–4분 | 방법: vcaml 원리 + 우리가 더한 것 |
| 4–9분 | **라이브 데모**: 정상 Meet 통화 → 노트북에서 손상 주입(Plan E) → 폰 화면, 버블(원인·조치), 대시보드가 함께 변화 → [조치] 버튼 (카카오는 "모델 추정값"으로 같이 보여 줌) |
| 9–11분 | 결과: 캡처 충실도, 정답 대비 정확도(+보정 효과), 진단 정확도(손실·대역폭), Meet·카카오 비교 |
| 11–12분 | 한계와 향후 과제 |

라이브 데모가 실패하면 즉시 Replay나 녹화본으로 전환한다.

## 10. 지금까지 확인한 것과 남은 위험

### 10-1. 이미 확인한 것 [확인됨, 10/13 기준]
- vcaml 원본 테스트 50개 통과. **학습 재현도 성공**: fps 오차 Meet 1.334 / Teams 1.812 / Webex 1.328로 솔로와 같고(평균 1.491, 논문 1.50).
- **실시간 1초 윈도우 feature가 vcaml 배치와 완전히 같은 값**임을 15통화로 확인했다.
- 모델 4개 + 진단이 1초 분량을 처리하는 데 **상위 5%에서도 36 ms**(목표 200 ms)다.
- **PCAPdroid → 노트북 실시간 수신**: 3.7분, 30,462 패킷이 앱의 연결 기록과 개수·바이트·시각까지 일치(수신률 사실상 100%). 파일 형식은 RAW(101). 다만 PCAPdroid가 1초씩 모아 보내서 **약 1초 지연**이 있다.
- **핫스팟 기본 성능**(집 5 GHz): 직결 대비 다운로드 -18%, 지연 +3 ms.
- **Clumsy는 핫스팟 경유 폰 트래픽에 효과 없음**(→ Plan E). gnirehtet·scrcpy는 USB 문제로 보류.
- **오버레이 스파이크**: Android 13에서 버블 표시, 더미 서버 수신, 설정 패널 열기, RSSI 읽기까지 동작.
- 합성 진단 실험(시뮬레이션): 대역폭 재현율 0.95–1.00, 손실은 RTP 순번이 있어야 0.56–0.94, 고정 지연은 불가.
- 도구: Wireshark 4.6.9, scrcpy 4.1, Clumsy 0.3, Flutter 3.41.4 설치됨.

**아직 없는 것(솔직하게)**: 폰에서 얻은 정답 데이터, 폰 통화 pcap 기반 정확도 수치, Live 연결, React 대시보드, 지표별 판정 기준. "모바일에서 검증했다"는 주장은 **W1–W5 실험 뒤에야** 할 수 있다.

## 11. 용어 사전

### 네트워크 기초
| 용어 | 쉬운 뜻 |
|---|---|
| **패킷 (packet)** | 데이터를 잘게 나눈 작은 상자. 영상통화는 1초에 수십~수백 개를 주고받는다 |
| **헤더 (header)** | 패킷의 송장. 누가 누구에게 보내는지, 크기가 얼마인지 |
| **페이로드 (payload)** | 패킷의 내용물(실제 영상·음성). 암호화돼서 볼 수 없다 |
| **IP / IP 주소** | 인터넷의 집 주소 체계. IP 헤더에 보낸 곳·받는 곳 주소가 있다 |
| **포트 (port)** | 한 집(기기) 안의 방 번호. 어느 앱으로 갈 데이터인지 구분한다 |
| **TCP** | 도착 확인을 하는 꼼꼼한 전송 방식. 빠짐없이 가지만 느릴 수 있다(웹페이지, 파일) |
| **UDP** | 확인 없이 계속 보내는 빠른 방식. 일부가 사라져도 계속 간다. 영상통화가 주로 쓴다 |
| **RTP** | 영상·음성을 UDP로 보낼 때 붙이는 추가 송장(프레임 번호, 시각). "앱 계층" 정보라 vcaml의 핵심 방법은 이것 없이 IP/UDP 헤더만 쓴다. 카카오톡이 RTP를 쓰는지는 미확인 |
| **WebRTC** | 브라우저에서 영상통화를 하게 해 주는 기술. Meet가 사용한다 |
| **getStats / webrtc-internals** | WebRTC 통화 중 브라우저가 실제 fps·bitrate 등을 알려 주는 기능. 우리 **정답**의 출처 |
| **Wi-Fi 핫스팟** | 노트북이나 폰이 공유기 역할을 해서 다른 기기에 인터넷을 나눠 주는 것 |
| **RSSI** | Wi-Fi 신호 세기. 단위 dBm, 0에 가까울수록 강하다(−50은 강함, −80은 약함). [가정] −75 이하를 "약한 Wi-Fi" 기준 후보로 둔다 |
| **VPN** | 기기의 데이터를 특정 통로로 돌리는 기능. PCAPdroid는 이것을 이용해 폰 안에서 패킷을 기록한다. Android는 VPN을 한 번에 하나만 켤 수 있다 |

### 품질 관련
| 용어 | 쉬운 뜻 |
|---|---|
| **손실 (packet loss)** | 보낸 패킷 중 도착하지 못한 비율(%). 화면이 깨지거나 멈춘다 |
| **지연 (delay, latency)** | 데이터가 도착하기까지 걸리는 시간(ms). 대화가 엇갈린다 |
| **지터 (jitter)** | 지연이 들쭉날쭉한 정도. 화면이 버벅인다 |
| **대역폭 (bandwidth)** | 길의 넓이 = 1초에 보낼 수 있는 최대 양. 좁으면 앱이 화질을 낮춘다 |
| **처리량 (throughput)** | 실제로 1초에 보낸 양. 속도 측정(speedtest)으로 잰다 |
| **RTT** | 왕복 시간. 갔다가 돌아오는 데 걸린 시간. `ping`으로 잰다 |
| **QoE** | 사용자 체감 품질. 처음엔 0–100 점수로 만들려 했으나 v5에서 **지표별 정상/주의/나쁨 판정**으로 바꿨다 |
| **혼잡 제어** | 네트워크가 막히면 앱이 스스로 보내는 양을 줄이는 기능. What-if는 이것을 재현하지 못한다 |

### 단위
| 단위 | 뜻 | 감 잡기 |
|---|---|---|
| **ms** | 밀리초 = 1/1000초 | 100ms = 0.1초 |
| **bps / kbps / Mbps** | 초당 비트 / 천 비트 / 백만 비트 | 1 Mbps = 1000 kbps. 1 byte = 8 bit |
| **fps** | 초당 프레임(화면 장수) | 30 부드러움, 15 약간 끊김 |
| **px** | 픽셀 | 해상도 높이 720px = HD |
| **dBm** | 신호 세기 단위(음수) | −50 강함, −80 약함 |
| **B (byte)** | 바이트 | vcaml은 UDP 길이가 306바이트를 넘는 패킷을 "영상 패킷"으로 본다 |

### 머신러닝·평가
| 용어 | 쉬운 뜻 |
|---|---|
| **feature (특징)** | 모델에 넣는 입력값. 우리는 1초 동안의 패킷 크기 통계와 간격 통계 |
| **Random Forest** | 여러 개의 "질문 나무"(결정 트리)가 투표해서 답을 내는 모델. vcaml이 쓴다 |
| **학습 / 추론** | 학습 = 정답이 있는 데이터로 규칙 익히기. 추론 = 새 데이터에 규칙 적용하기 |
| **정답 (ground truth)** | 비교 기준이 되는 진짜 값. 우리는 Meet의 getStats (카카오는 정답 없음) |
| **슬라이딩 윈도우** | 데이터를 1초씩 잘라 차례로 처리하는 것 |
| **k-fold 교차검증** | 데이터를 k(=5)등분해서 돌아가며 시험용으로 쓰는 공정한 평가법 |
| **MAE** | 평균 절대 오차. 작을수록 좋다. fps MAE 1.5 = 평균 1.5프레임 틀림 |
| **±2 fps 정확도** | 오차가 2fps 이내인 비율 |
| **Precision (정밀도)** | "저하"라고 판정한 것 중 진짜 저하인 비율. 헛경보가 적을수록 높다 |
| **Recall (재현율)** | 진짜 저하 중 "저하"라고 잡아낸 비율. 놓친 것이 적을수록 높다 |
| **F1** | Precision과 Recall의 조화 평균. 둘 다 좋아야 높다 |
| **Confusion Matrix (혼동 행렬)** | "정답 × 예측" 표. 무엇을 무엇으로 헷갈렸는지 보인다 |
| **일반화** | 학습한 환경(데스크톱)과 다른 환경(모바일)에서도 잘 맞는가 |
| **pickle (pkl)** | 학습된 모델을 저장한 파일 형식 |
| **MLflow** | 학습 실험 기록(설정, 오차, 모델 파일)을 관리하는 도구. vcaml이 쓴다 |

### 12-1. 3분 설명 스크립트 (v5)
1. **문제 (30초)**: "영상통화 앱은 데이터를 암호화하기 때문에, 앱 밖에서는 통화 품질을 알기 어렵습니다. IMC 2023의 vcaml 연구는 패킷의 크기와 간격만으로 데스크톱 통화의 fps 등을 평균 1.5프레임 오차로 추정했습니다."
2. **우리 질문 (30초)**: "이것이 **모바일에서도, 실시간으로도** 맞는지가 목표입니다. 정확히는, Android 폰 안의 VPN 캡처만으로 데스크톱에서 학습한 모델이 모바일 통화를 얼마나 정확히 추정하는지, **그리고 오차가 캡처 왜곡 때문인지 모델 일반화 실패 때문인지**를 구분해서 검증합니다."
3. **방법 (60초)**: "폰의 PCAPdroid로 패킷을 노트북에 실시간으로 보내 vcaml 모델로 1초마다 추정합니다. 결과는 폰 위 오버레이와 웹 대시보드에 지표별 판정으로 보여 줍니다. 이미 vcaml 재현에 성공했고(오차 1.49 대 논문 1.50), 실시간 처리가 배치와 같은 값을 내며 1초 분량을 36 ms에 처리하고, PCAPdroid 수신이 앱 기록과 정확히 일치함을 확인했습니다."
4. **검증 (40초)**: "① 폰 캡처와 노트북 쪽 캡처를 동시에 비교하는 충실도 실험 ② Meet의 getStats를 정답으로 한 정확도 실험 ③ 노트북을 통화 상대로 두고 손실·대역폭을 걸어 원인 표시를 검증하는 실험, 세 가지를 합니다. 카카오톡은 정답이 없어 추정값과 정성 비교로만 다룹니다."
5. **일정·역할 (20초)**: "Sungmin이 서버·모델·오버레이, 팀원이 React 대시보드를 맡고, 11/24 기능 동결 후 12/2에 발표합니다."

### 12-2. 교수님께 여쭤볼 것 (v5)
1. **평가 방향**: 이 프로젝트에서 "vcaml에 없는 기능"을 **모바일 측정 검증**(캡처 충실도, 정답 대비 정확도, 일반화)으로 인정해 주시는지. UI·앱 구현과 연구 검증의 비중은 어떻게 보시는지.
2. vcaml 원본에 **라이선스 파일이 없습니다**. fork + submodule(코드 복사 없이 링크)로 쓰고 출처를 밝히는 방식이 괜찮은지.
3. 정답이 없는 **카카오톡 결과를 "모델 추정값, 정성 비교"로만** 제시해도 충분한지.
4. 학교 Wi-Fi(igc_user)에서 **노트북 핫스팟으로 폰을 연결하고 패킷을 캡처**하는 실험, 그리고 **노트북에서 Clumsy로 손상을 거는 시연**을 발표장에서 해도 되는지.
5. 점수 대신 **지표별 판정**을 쓰는 것이 괜찮은지(기준은 공개 자료에서 가져옴).
6. 최종 보고서의 형식과 마감(현재 [가정] 12/12).

### 12-3. 예상 질문과 답
| 질문 | 답 |
|---|---|
| vcaml과 무엇이 다른가? | vcaml은 데스크톱·오프라인이다. 우리는 **모바일 폰 안에서 캡처**해 실시간으로 추정하고, 그 정확도가 캡처 방식 때문에 달라지는지를 **따로 검증**한다. 원인 표시와 조치 안내를 더했다 |
| 그냥 vcaml을 폰으로 옮긴 것 아닌가? | 옮기는 것 자체는 엔지니어링이다. 기여는 **"폰 안 캡처가 모델 입력을 얼마나 왜곡하는지"와 "데스크톱 모델이 모바일에서 얼마나 틀리는지"를 수치로 분리해 보고**하는 것이다. 이 수치는 아직 실험 전이다 |
| 카카오톡은 정답이 없는데? | 정량 평가는 정답이 있는 Meet로 한다. 카카오톡은 "모델 추정값"으로 표시하고 Meet와 정성 비교한다. (하루 파일럿으로 화면 기반 정답이 가능한지도 확인해 본다) |
| 원인 진단은 믿을 만한가? | 대역폭 부족과 패킷 손실에 한정하고, 신뢰도와 함께 "가능성"으로 표시한다. 지금 수치는 데스크톱 기록에 합성한 시뮬레이션이고, 폰 실험으로 다시 확인한다. 고정 지연과 약한 Wi-Fi는 정량 평가에서 뺐다 |
| 왜 점수가 아니라 지표별 판정인가? | 100점 기준에 근거가 없고, 사람이 매긴 점수가 없어 검증할 수 없기 때문이다. 공개된 기준값에 출처를 달아 지표별로 판정한다 |
| 왜 노트북이 통화 상대인가? | 실측 결과 Windows 핫스팟을 지나는 폰 트래픽에는 Clumsy가 적용되지 않았다. 노트북 자신의 송신 트래픽에는 적용되므로 노트북이 영상을 보내게 했다. 대역폭을 줄이면 앱이 실제로 화질을 낮추는 진짜 반응도 얻는다 |
| 데모가 실패하면? | Replay 모드(녹화 재생)와 녹화본으로 즉시 전환한다 |
| 개인정보 문제는? | 우리 기기 트래픽만 기록하고, 내용은 암호화돼서 보지 않으며 크기와 시각만 쓴다 |

### 12-4. 타 프로젝트·서비스와의 비교, 독창성, 발전 가능성 (10/13 조사 기준)

#### (1) 한눈에 보는 위치
> **비슷한 것은 많지만 같은 것은 없다.** 통화 품질을 재는 도구들은 대부분 **직접 테스트 트래픽을 만들어 망을 재거나**, **자기 앱 안의 통계를 읽는다.** 우리처럼 **남의 통화 앱(Meet, 카카오톡)을 밖에서 관찰해 추정**하는 것은 vcaml 계열 연구뿐이고, 그것은 **망(네트워크) 쪽 관찰**이지 **폰 안 관찰**이 아니다.

| 구분 | 무엇을 재나 | 데이터를 어디서 얻나 | 우리와의 관계 |
|---|---|---|---|
| **vcaml** (IMC 2023) | 통화 중 fps·bitrate·jitter·해상도를 **추정** | 외부에서 본 패킷(IP/UDP 헤더) | **기반이자 유일한 직접 경쟁**. 데스크톱·오프라인, 모바일 단말 캡처는 다루지 않음. 라이선스 파일 없음 |
| **OpenTok / Vonage 네트워크 테스트** | 통화 **전에** 이 망으로 화상통화가 될지 점검 | 자사 SDK의 통계 + 직접 만든 테스트 통화 | **비경쟁**(방식이 다름). 단, **해상도별 bitrate·손실 판정 표**는 우리 판정 기준의 출처로 참고 가능. 두 저장소 모두 2026년 상반기에 **보관(archived)** 처리되어 통합 저장소로 넘어감 |
| **PacketLossTest / OpenPacketLoss** | 망의 **패킷 손실·지연·지터** | 브라우저가 직접 만든 WebRTC 데이터 채널 | **비경쟁**. 통화 품질이 아니라 망 상태. 2026-04 시작된 초기 단계(MIT) |
| **Cutie** | 망 품질을 **MOS 점수**로 연속 측정 | 직접 만든 probe(초당 10개) | **비경쟁**. 단순화한 E-model 공식으로 점수를 내지만 **검증은 없고 스스로 beta**라고 밝힘. 우리가 점수를 포기한 이유(검증 불가)의 사례 |
| **Internet Quality** (iOS 앱) | 개인 Wi-Fi·인터넷 속도, 지연, 손실, 점수 | 직접 측정 | **부분 겹침**: "Wi-Fi 문제인가, 인터넷 문제인가"를 나누는 발상이 우리 원인 표시와 닮음. 통화 품질 추정은 아님. iOS 전용 |
| **Zoom 패킷 분석 연구**(Michel 외, IMC 2022) | Zoom의 평문 헤더로 bitrate·프레임·지연·지터 계산 | 망 쪽 패킷 | **부분**: Zoom 전용 헤더에 의존. 카카오톡에는 적용 불가 |
| **암호화 통화 QoE 추정 연구**(Sidorov 외 2025, Berger 외 2025) | Zoom·WhatsApp의 fps·해상도·화질 점수를 ML로 추정 | 망 쪽 패킷, 앱과 무관한 정답(영상 기반) | **부분**: 같은 문제를 푸는 최신 연구. **망 쪽·오프라인**이고 폰 안 캡처가 아님. WhatsApp 연구는 fps ±2 정확도 85.2%를 보고 |
| **MopEye** (USENIX 2017) | 앱별 **지연**만 | 폰 안 VPN | **부분**: "폰 안 VPN으로 측정"의 선례. 영상 품질은 아님 |
| **PCAPdroid** | (측정 아님) 폰 패킷 캡처 | 폰 안 VPN | **우리의 입력 도구**. 공식 문서가 "비루팅 캡처는 헤더를 합성하고 크기·타이밍 분석에는 맞지 않을 수 있다"고 경고 → **우리의 핵심 검증 대상** |
| **통화 앱 위 품질 진단 오버레이** | — | — | 공개된 사례를 **찾지 못했다**(검색 범위 제한, 단정은 못 함) |

#### (2) 독창성: 어디가 새롭고, 어디가 새롭지 않은가
**새롭다고 주장할 수 있는 것 (실험으로 증명해야 함)**
1. **폰 안(VPN) 캡처 기준의 정확도**: vcaml과 최신 연구는 망 쪽 패킷을 쓴다. 폰 안 캡처가 입력을 얼마나 왜곡하고, 그 때문에 추정이 얼마나 틀리는지를 **수치로** 보여 주는 연구는 못 찾았다.
2. **오차의 원인 분리**: "틀린 이유가 캡처 왜곡인가, 데스크톱 모델의 모바일 일반화 실패인가"를 **같은 통화에서 동시 캡처(폰 vs 노트북 핫스팟)** 로 나눠서 본다.
3. **모바일 + 실시간 + 사용자에게 바로 표시**: 추정 결과를 통화 앱 위 오버레이로 보여 주는 구성 자체는 확인된 선행 사례가 없다(단, 이것만으로는 기술 기여가 약하고 UI 구현에 가깝다).

**새롭다고 주장하면 안 되는 것**
- 패킷 크기·간격으로 통화 품질을 추정한다는 **아이디어 자체**(vcaml과 후속 연구들이 이미 했다).
- "QoE를 측정했다"는 표현. 우리는 **추정**하며, 사람의 주관 평가(MOS)는 받지 않는다.
- 카카오톡의 정량 정확도(정답이 없다. 하루 파일럿이 성공해야 말할 수 있음).
- 원인 "진단"의 일반적 정확도. 지금 숫자는 **데스크톱 기록에 소프트웨어로 합성한 시뮬레이션**이고 폰 데이터는 0건이다.

**현재 증거 수준 (정직한 평가)**
| 주장 | 근거 | 수준 |
|---|---|---|
| vcaml을 재현할 수 있다 | 학습 재현 오차 1.49 (논문 1.50) | 실측, 데스크톱 데이터 |
| 실시간 처리가 배치와 같은 값을 낸다 | 15통화, 완전 일치 | 실측, 데스크톱 데이터 |
| 폰 패킷을 노트북으로 실시간 수신 가능 | 30,462패킷이 앱 기록과 일치 | 실측, 폰 |
| 폰 캡처 기준 추정이 정확하다 | **아직 없음** | 미검증 |
| 원인 표시가 정확하다 | 합성 시뮬레이션 (대역폭 0.95–1.00, 손실 0.56–0.94) | 시뮬레이션, 폰 데이터 없음 |

#### (3) 한계와 약점 (교수님이 지적하실 만한 것)
- **"그냥 vcaml을 폰에 옮긴 것"으로 보일 수 있다.** → 그래서 기여를 "옮기기"가 아니라 "옮겼을 때의 오차를 분리해 보고"하는 쪽에 두었다.
- **정답(getStats)을 폰에서 받을 수 있는지가 아직 미확인**이다. 안 되면 정확도 주장이 줄어든다(대안: 충실도 실험 중심).
- **표본이 작다**(Meet 20통화 정도 예정, 숫자는 [가정]). 일반화는 주장하지 않는다.
- **루팅 기기가 없어** PCAPdroid 비루팅 모드 하나만 다룬다.
- vcaml 원본에 **라이선스가 없어** 우리 결과물의 재배포 범위가 제한될 수 있다.

#### (4) 발전 가능성 (이 프로젝트 이후)
수업 범위 밖이므로 "가능성"으로만 쓰고, 실현 여부는 확인하지 않았다.

| 방향 | 내용 | 근거·조건 |
|---|---|---|
| **더 많은 앱** | Zoom, Teams, WhatsApp 등으로 확대 | vcaml이 Meet·Teams·Webex를 다뤘고 최신 연구가 Zoom·WhatsApp를 다룸. 앱마다 임계값이 달라지는 것을 이미 합성 실험에서 확인했으므로 **앱별 보정이 필요** |
| **더 나은 정답** | 카카오톡 같은 정답 없는 앱을 **화면 녹화로 센 fps**로 검증 | 하루 파일럿으로 가능성 확인 예정. 최신 연구(Berger 2025)가 앱과 무관한 정답을 쓰는 선례 |
| **폰 데이터로 재학습** | 폰에서 모은 Meet 데이터로 모델을 다시 학습 | 이번에 모은 데이터가 곧 학습 자료가 됨. 데이터가 충분한지는 미확인 |
| **원인 진단을 ML로** | 규칙 기반 → 라벨이 충분히 쌓이면 학습 모델 | 지금은 라벨이 부족해 규칙 기반이 맞다. 폰에서 손상 라벨 데이터가 생기면 가능 |
| **루팅 기기와 비교** | 비루팅 vs 루팅(왜곡 없는 캡처)으로 PCAPdroid 한계를 정량화 | 루팅 기기가 필요(현재 없음) |
| **폰 안 실행** | 노트북 없이 폰에서 직접 추정 | 현재 모델(Random Forest, 약 30MB)과 파이프라인은 노트북 기준. 폰 이식 가능성은 **미확인** |
| **사용자 평가 연결** | 사람이 매긴 점수(MOS)와 비교 | 사용자 실험이 필요. 이번 범위 밖 |
| **iPhone** | iOS에서도 | iOS의 패킷 캡처 방식·권한은 **미확인** |

**한 줄 결론 (면담용):** "새로운 알고리즘을 만든 것이 아니라, 이미 있는 방법(vcaml)이 **폰 안에서도 통하는지, 통하지 않는다면 왜인지**를 처음으로 정량화하려는 프로젝트입니다. 결과가 좋으면 모바일 적용 근거가 되고, 나쁘면 "어디서 무너지는지"가 결과가 됩니다."

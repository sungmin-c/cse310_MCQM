## 1. "WebRTC 네트워크를 측정하면, 그다음은 뭔가?"
> 질문 원문(사용자 전언): *"you measure the WebRTC's network then what?"* — repo에는 원문 기록이 없다. 아래는 질문을 "측정만으로 무슨 가치가 있나"로 읽은 답이다. 뜻이 다르면 면담 때 한 번 되묻는다.

**한 문장 답**: 측정은 입력이고, 출력은 *"품질이 떨어졌고, 원인이 네트워크인지 이 기기인지, 무엇을 하라, 했더니 돌아왔나"*다. 패킷만 재면 틀리는 경우를 실측으로 보였다.

## 2. "모니터가 자원을 침범해 통화 성능을 떨어뜨리지 않나?"
**구조**: 모니터는 수동 캡처라 패킷을 막거나 보내지 않는다(네트워크 영향 0). 남는 경로는 CPU·RAM 경쟁이고, 이게 **간접으로** 통화에 닿을 수 있다 — CPU가 모자라면 Chrome이 송신 fps·bitrate를 낮춰 *상대방* 화질이 떨어진다(P2-2에서 송신 fps 16.5→3.5가 실제로 관측됨).

**지금까지 측정된 것 (P3, Meet 1통화, 배터리 상태, 모니터 끔/켬 각 50초×3회)** [확인됨]
| 지표 | 끔 | 켬 |
|---|---|---|
| 모니터 CPU (tshark+python) | — | **1.27%** (±0.31) |
| Chrome CPU / 전체 CPU | 9.2% / 22.7% | 8.9% / 23.7% |
| 수신 fps / 디코드 fps | 28.16 / 29.78 | 28.20 / 29.79 |
| 디코드 시간 | 5.78 ms | 5.70 ms |
| freeze / 드롭 | 0.05 / 0 | 0 / 0 |
| 송신 fps | 29.16 | 28.76 |
- 다른 파일럿에서도 모니터 CPU는 P1 평균 1.4%(최대 2.5%), Zoom P4 0.9%.
- 1 tick 처리: 벤치 p95 36 ms, 실통화(배터리) p50 81·p95 126 ms. 목표 200 ms 이내.
- 결론: *여유 CPU(전체 23%)에서는* 통화 지표 차이가 단계 간 변동 안이다.

**아직 측정 안 된 것 — 그래서 질문이 정당하다**: P3는 ① 전체 CPU 23%(여유)에서만, ② 위젯 없이, ③ 코어 고정 없이(모니터가 빈 코어에서 돌아 경쟁이 숨음), ④ 배터리 상태, ⑤ 통화 1건이었다. 이 5개 중 ①–④를 주말 P5가 메운다. ⑤는 한계로 남는다.

## 5. 예상 반박과 답
**R1. 기기 CPU 때문에 품질이 떨어지는 건 당연하지 않나?**
→ 당연한 건 효과가 아니라 *관측 가능성*이다. P2에서 수신 fps(vcaml이 쓰는 라벨)는 끝까지 정상이었다. 그래서 정답을 freeze·디코드 시간·송신 fps로 다시 정의했다.

**R2. 모니터 CPU 1.3%면 문제없다는 건 너무 쉬운 결론 아닌가?**
→ 맞다. P3는 CPU가 남는 조건이었다. 포화·같은 코어·RAM 압박은 P5에서 처음 본다. 주말 결과를 표로 가져온다 [빈칸이면: 아직 실측 전이라고 그대로 말한다].

**R3. 합성 실험 결과를 실제 성능으로 말해도 되나?**
→ 안 된다. in-lab trace에 손상을 삽입한 것이고, 실제 Clumsy 주입은 W3 S0에서 검증한다. 실패하면 해당 조건을 보류한다.

**R4. 통화 1건으로 결론을 내도 되나?**
→ 안 된다. 파일럿이라 부르고 방향 확인용으로만 쓴다. 통계적 주장은 W3–W5 반복 수집 뒤.

**R5. 조치=주입 해제면 회복 검증은 순환 아닌가?**
→ 맞다. 조치의 효과는 주장하지 않는다. 회복 판정의 지연·오판정(해제 전 "회복" 오보)·해제 후에도 안 돌아오는 경우를 잰다.

**R6. 앱 간 비교 벤치마크나 타 팀 합류는?**
→ 정답 부재와 일정으로 기각했다(Q27).

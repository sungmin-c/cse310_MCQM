## 1. 배경: vcaml은 무엇을 했나

### 1-1. 문제
영상통화 앱(Meet, 카카오톡 등)은 데이터를 **암호화**해서 보낸다. 그래서 통신사나 공유기 입장에서는 "지금 이 사람 통화 화질이 좋은지 나쁜지"를 직접 알 수 없다.

### 1-2. 택배 비유
인터넷 데이터는 **패킷(packet)** 이라는 작은 상자로 쪼개져서 오간다.

| 택배 | 인터넷 |
|---|---|
| 상자 | 패킷 |
| 송장(보내는 곳, 받는 곳, 무게) | **헤더(header)** — IP 주소, 포트, 길이 |
| 상자 안 내용물 | **페이로드(payload)** — 실제 영상·음성. 암호화돼서 못 본다 |

vcaml의 아이디어:
> 상자를 열지 않아도 **상자 크기와 도착 간격**만 보면 내용물을 짐작할 수 있다.
> 예: 큰 상자가 촘촘하게 많이 오면 → 고화질 영상이 잘 오고 있다. 상자가 띄엄띄엄 오면 → 화면이 끊기고 있을 가능성이 높다.

### 1-3. 어떻게 추정하나 (머신러닝)
1. 통화 중 패킷을 기록한다(= **pcap** 파일).
2. 1초 단위로 잘라서, 그 1초 동안 패킷 크기의 평균·최대·개수, 패킷 사이 간격의 평균·편차 같은 **통계값(feature, 특징)** 을 계산한다. vcaml에서는 이것을 `LSTATS`(크기 통계), `TSTATS`(간격 통계)라고 부른다.
3. 같은 1초 동안 브라우저가 기록한 **진짜 품질 값(정답)** 을 함께 놓고, **Random Forest**라는 머신러닝 모델에게 "이런 통계가 나오면 화면은 몇 fps였다"를 학습시킨다.
4. 학습된 모델에 새 통화의 통계만 넣으면 품질을 추정한다.

### 1-4. 무엇을 추정하나 (4가지 지표)
| 지표 | 뜻 | 단위 | 감 잡기 |
|---|---|---|---|
| **fps** (frame rate) | 1초에 화면이 몇 장 바뀌나 | frames/s | 30이면 부드럽고, 10 이하면 뚝뚝 끊김 |
| **bitrate** | 1초에 받는 데이터 양 | kbps (초당 킬로비트) | 높을수록 보통 화질이 좋다 |
| **frame jitter** | 화면 장면 사이 간격이 얼마나 들쭉날쭉한가 | ms (1/1000초) | 클수록 화면이 버벅인다 |
| **resolution** (frame height) | 화면 세로 해상도 | px (픽셀) | 720 = HD, 360 = 저화질 |

### 1-5. 논문 결과와 솔로 프로젝트 재현 [확인됨]
Sungmin이 솔로 프로젝트에서 vcaml을 Windows 노트북으로 재현했다(결과는 솔로 `docs/2. RUN_GUIDE.md`).

| 항목 | 논문 | 우리 재현 |
|---|---|---|
| fps 평균 오차 (IP/UDP 헤더만 쓴 ML) | 1.50 프레임 | **1.49 프레임** |
| fps 평균 오차 (RTP 헤더까지 쓴 ML) | 1.33 | 1.38 |
| 해상도 정확도 (Meet) | 97.74% | 97.75% |

→ "평균 1.5 프레임 정도만 틀린다"는 뜻이다. 화면이 실제로 30fps면 28.5~31.5 정도로 맞힌다.

### 1-6. vcaml의 한계 (= 우리 프로젝트의 출발점)
- **데스크톱 PC**에서 측정한 데이터만 있다(Meet, Teams, Webex). 모바일·카카오톡은 없다.
- **오프라인**: 통화가 끝난 뒤 파일로 한꺼번에 분석한다. 실시간이 아니다.
- 화면도, 사용자용 앱도 없다(연구용 코드).
- 논문에서도 실험실 데이터로 학습한 모델을 실제 가정 환경에 쓰면 Meet에서 오차가 크게 늘었다(솔로 노트 기준). → **환경이 바뀌면 정확도가 떨어질 수 있다.** 우리가 모바일에서 "얼마나 정확한가"를 검증해야 하는 이유다.

## 3. 전체 구조 (데이터가 흐르는 길)

```
 ┌──────────────── Galaxy S20 (Sungmin 폰) ────────────────┐
 │  카카오톡/Meet 영상통화  ←→  (상대: 팀원 iPhone)        │
 │        │                                                │
 │   PCAPdroid 앱: 폰이 주고받는 패킷을 기록(캡처)          │
 │        │                       ┌──────────────────────┐ │
 │        │                       │ 오버레이 버블 (Flutter)│ │
 │        │                       │ ● 실패  QoE 46        │ │
 │        │                       │ 원인: 패킷 손실        │ │
 │        │                       │ [조치] Wi-Fi 설정 열기 │ │
 │        │                       └──────────▲───────────┘ │
 └────────┼──────────────────────────────────┼─────────────┘
          │ 패킷 스트림 (USB 또는 Wi-Fi)       │ 결과 (WebSocket)
          ▼                                  │
 ┌──────────────── 노트북 (Windows) ──────────┼─────────────┐
 │  ① 1초씩 자르기 → ② 통계 계산(feature)                    │
 │  → ③ vcaml 모델로 fps·bitrate·jitter·해상도 추정           │
 │  → ④ QoE 점수(0–100) → 통과/실패 → 원인 진단 → 조치 문구    │
 │  → ⑤ WebSocket 서버가 1초마다 결과를 보냄 ─────┬──────────┘
 │                                                 ▼
 │                        React 웹 대시보드 (팀원 담당)
 │                        그래프, 정답 비교, What-if 슬라이더
 └──────────────────────────────────────────────────────────┘
```

**중요**: 모든 계산(추론)은 **노트북**에서 한다. 폰의 오버레이와 웹 대시보드는 **결과를 받아서 보여 주기만** 한다. 둘은 같은 형식의 메시지(`docs/SCHEMA.md`)를 받는다.

### 3-1. 단계별 설명
| 단계 | 하는 일 | 쓰는 것 |
|---|---|---|
| 캡처 | 폰의 패킷을 기록한다. PCAPdroid는 폰 안에 "가짜 VPN"을 만들어 모든 데이터가 그곳을 거치게 해서 기록한다(루팅 불필요) | PCAPdroid 앱 |
| 전송 | 기록한 패킷을 노트북으로 실시간으로 보낸다 | PCAPdroid의 TCP exporter(문서가 실시간용으로 권장) 또는 USB |
| 추정 | 1초 단위 통계를 계산해 vcaml 모델에 넣는다 | Python, vcaml, scikit-learn |
| 점수·판정 | 4개 지표를 0–100 QoE 점수로 바꾸고 임계값(예: 70) 이상이면 "통과" | `qoe.py` (앞으로 작성) |
| 진단 | 품질이 나쁘면 원인을 추정한다: 대역폭 부족 / 지연·떨림 / 패킷 손실 / 약한 Wi-Fi | `diagnosis.py` (앞으로 작성) |
| 전달 | 1초마다 결과 메시지를 보낸다 | WebSocket (FastAPI) |
| 표시 | 폰에는 작은 버블, 노트북에는 분석 화면 | Flutter, React |

### 3-2. QoE 점수란
**QoE(Quality of Experience)** = 사용자가 체감하는 품질. fps·bitrate·jitter·해상도를 합쳐 **0–100점** 하나로 만든다.
공식은 ITU-T(국제전기통신연합) **G.1070**(영상통화 품질 추정 모델) 계열을 **참고만** 해서 만들고, 각 계수에 근거를 주석으로 단다. "표준을 지켰다"고 주장하지 않는다.
손실이나 지연이 늘면 점수가 **절대 올라가지 않는지**(단조성) 테스트로 확인한다.

## 4. 세 가지 입력 모드

| 모드 | 무엇 | 언제 쓰나 | 비유 |
|---|---|---|---|
| **Live** | 지금 진행 중인 통화를 실시간 분석 | 데모의 핵심 | 생방송 |
| **Replay** | 미리 녹화한 pcap 파일을 실시간처럼 재생 | 개발, 그리고 데모 당일 Live가 실패할 때의 대안 | 녹화 방송 |

## 5. 데모 계획 — 일부러 네트워크를 나쁘게 만들기

발표 때 "정상 통화 → 네트워크를 일부러 망가뜨림 → 폰 화면과 대시보드가 함께 나빠짐"을 보여 주려면, **폰과 인터넷 사이에 끼어들어 손상을 넣을 장치**가 필요하다.

### Plan A (기본): 노트북 핫스팟 + Clumsy
```
인터넷 ←─ 학교 Wi-Fi(igc_user) ←─ 노트북 ──핫스팟──→ 폰
                                    │
                               Clumsy가 여기서
                         손실·지연·대역폭 제한을 넣음
```
- 노트북이 학교 Wi-Fi에 붙은 상태에서 **모바일 핫스팟**을 켜고, 폰을 그 핫스팟에 연결한다. 그러면 폰의 모든 데이터가 노트북을 거친다.
- **Clumsy**(Windows 프로그램, 관리자 권한 필요)로 그 길목에 일부러 문제를 만든다.
  - drop: 패킷을 일정 비율로 버린다 → **손실**
  - lag: 패킷을 늦게 보낸다 → **지연**
  - bandwidth: 속도를 제한한다 → **대역폭 부족** (Clumsy 0.3 소스에 있음 [확인됨])
- **미확인**:
  - 노트북 하나의 Wi-Fi로 받으면서 동시에 핫스팟을 내보내면 속도가 얼마나 떨어지는지. 그래서 **손상을 넣기 전의 기본 성능(baseline)부터 측정**한다.
  - Clumsy가 "노트북을 거쳐 가는 남의(=폰의) 트래픽"에도 적용되는지. 문서에 언급이 없다.
  - 학교망 정책상 핫스팟 공유가 허용되는지.

### Plan B: gnirehtet (USB 역테더링)
폰의 인터넷을 USB로 노트북을 통해 쓰게 하는 도구다. 단점은 두 가지다.
- Android에서 VPN 자리를 하나만 쓸 수 있어 **PCAPdroid와 동시에 못 쓸 가능성이 크다**(미확인).
- 2.5.1 이후 사실상 유지보수가 끝났다.

### Plan C: What-if 모드로 대체
라이브 손상 주입이 안 되면, 녹화 기록에 가상 손상을 넣는 What-if로 시연한다.

### 화면 배치
왼쪽에는 **scrcpy**로 폰 화면을 노트북에 띄운다(실제 통화 화면과 그 위의 오버레이 버블). 오른쪽에는 웹 대시보드를 둔다.

## 6. "정확하다"를 어떻게 증명하나 (검증 실험 4가지)

이 프로젝트의 핵심 결과물이다.

### 실험 ① 캡처 충실도: "폰에서 기록한 데이터 자체가 정확한가?"
- PCAPdroid는 폰 안의 가짜 VPN에서 기록하므로, 실제 전파로 오간 패킷과 **시간·크기가 조금 다를 수 있다**.
- 방법: 같은 통화를 (a) 폰의 PCAPdroid와 (b) 노트북 핫스팟 쪽 Wireshark로 **동시에** 기록하고 비교한다. 패킷 수, 크기 분포, 간격 분포, 추정 결과를 본다.
- 결과: "차이가 ○○% 정도다"를 숫자로 보고한다.

### 실험 ② 정답 대비 정확도: "추정값이 진짜 값과 얼마나 가까운가?"
- **정답(ground truth)** 은 Chrome 브라우저의 **getStats**에서 얻는다. WebRTC 통화 중 브라우저가 실제 fps·bitrate 등을 알려 주는 기능이다.
  - 그래서 정답은 **폰 Chrome으로 하는 Meet 통화에서만** 얻을 수 있다.
  - 카카오톡은 정답을 볼 방법이 없다 → 결과에 항상 `validated: false`, "모델 추정값"으로 표시한다.
- 폰 Chrome에서 getStats를 1초마다 수집할 수 있는지는 **미확인**이다. M0에서 가능 여부부터 확인한다.
- 지표:
  - **MAE** (평균 절대 오차): 정답 30, 추정 28이면 오차 2. 이것들의 평균.
  - **±2 fps 정확도**: 오차가 2 이내인 초의 비율.
  - **Precision / Recall / F1 / Confusion Matrix**: "정상/저하" 판정이 맞았는지(설명은 11장).
- **일반화**: 데스크톱 데이터로 학습한 모델 vs 폰 Meet 데이터로 다시 학습(또는 보정)한 모델의 정확도를 비교한다.

### 실험 ③ 원인 진단 정확도: "원인을 맞게 짚는가?"
Clumsy로 **어떤 손상을 넣었는지 우리가 알고 있으므로**, 그것을 정답 라벨로 쓴다.

| Clumsy로 넣은 것 | 정답 라벨 |
|---|---|
| drop (패킷 버림) | `loss` (손실) |
| lag (지연) | `delay_jitter` (지연·떨림) |
| bandwidth (속도 제한) | `bandwidth` (대역폭 부족) |
| 아무것도 안 넣음 | `none` |

- 지표: 원인별 Precision·Recall, Confusion Matrix, 그리고 손상 시작부터 맞게 진단하기까지 걸린 시간(초).
- **약한 Wi-Fi(`weak_wifi`)** 는 Clumsy로 만들 수 없다. 폰을 공유기에서 멀리 옮기면서 오버레이 앱이 보내는 **RSSI**(Wi-Fi 신호 세기) 값과 함께 **정성적으로만** 확인한다.

### 실험 ④ 앱 간 비교: Meet vs 카카오톡
같은 손상 조건에서 두 앱의 추정·진단 결과를 비교한다. 카카오톡은 정답이 없으므로 "정성 비교"로 표기한다.

### 한계 (발표와 보고서에 그대로 적는다)
- 정답은 Meet에만 있고, 표본 수가 적다.
- What-if는 시뮬레이션이다.
- 진단 라벨은 인위적으로 만든 손상이다.
- PCAPdroid 캡처 방식이 측정에 영향을 줄 수 있다.

### 8-2. 한 저장소(repo)에서 충돌 없이 일하는 법
- GitHub repo: `sungmin-c/cse310_MCQM` (public)
- **폴더 주인 정하기**: 자기 폴더만 고친다. 상대 폴더는 리뷰만 한다.
  ```
  cse310_MCQM/
  ├─ vcaml/        ← vcaml 원본 코드 (submodule, 아래 설명)      [Sungmin]
  ├─ server/       ← Python 서버                                [Sungmin]
  ├─ capture/      ← 캡처 수신 코드 (예정)                      [Sungmin]
  ├─ overlay/      ← Flutter 오버레이 앱 (예정)                 [Sungmin]
  ├─ tests/        ← Python 테스트                              [Sungmin]
  ├─ dashboard/    ← React 대시보드 (예정)                      [팀원]
  ├─ docs/         ← 명세, 일정, 메시지 형식, 이 문서          [공동]
  └─ data/         ← 데이터 (git에 안 올라감)                  [각자 PC]
  ```
- **브랜치 규칙**: `main`은 항상 실행 가능한 상태로 둔다. 작업은 `ml/주제`, `web/주제` 같은 브랜치에서 하고 PR로 합친다.
- **SCHEMA = 둘 사이의 계약서**: 서버가 보내는 메시지 모양을 `docs/SCHEMA.md`에 적고, 예시 6줄을 `docs/schema/sample.jsonl`에 둔다. 양쪽 테스트가 이 예시로 검사한다. 한쪽이 마음대로 바꾸면 테스트가 실패한다.
- **팀원이 서버 완성을 기다리지 않게**: 가짜 데이터를 1초마다 보내는 **더미 서버**가 이미 있다. 팀원은 Mac에 uv만 설치하면 된다.
  ```
  uv run server/dummy_stream.py      # → ws://localhost:8000/ws 로 1초마다 메시지
  ```
  [확인됨] 1.01초 간격으로 메시지가 오는 것을 확인했다.

### 8-3. vcaml 코드를 가져오는 방식 (fork + submodule)
- **fork**: 원본 vcaml을 내 GitHub 계정으로 복제한 것이다(`sungmin-c/vcaml`). 원본을 건드리지 않고 고칠 수 있다.
- **submodule**: 우리 repo 안에 vcaml 코드를 **복사하지 않고, "fork의 이 버전을 쓴다"는 링크만** 넣는 방식이다.
- 이렇게 한 이유: vcaml 원본에는 **LICENSE(사용 허가) 파일이 없다** [확인됨]. 라이선스가 없는 코드를 우리 public repo에 통째로 복사하면 재배포가 될 수 있어서 링크 방식을 택했다. 법률 판단은 아니다. **교수님께 확인할 사항**이다.
- 원본에서 바꾼 것: 설정 2줄뿐이다(데이터 폴더 위치, 다운로드 스크립트 경로 버그).

### 8-4. 데이터 재사용
솔로 프로젝트에서 받아 둔 데이터 약 15GB(실험실 2.2GB, 실사용 8.4GB, 학습 결과 4.2GB)를 **복사하지 않고 바로가기(junction)로 연결**했다. 솔로 자료는 읽기만 하고 수정하지 않는다. 수정되지 않았는지는 파일 지문(SHA256)으로 확인했다.

## 11. 용어 사전

### 네트워크 기초
| 용어 | 쉬운 뜻 |
|---|---|
| **패킷 (packet)** | 데이터를 잘게 나눈 작은 상자. 영상통화는 1초에 수십~수백 개를 주고받는다 |
| **헤더 (header)** | 패킷의 송장. 누가 누구에게 보내는지, 크기가 얼마인지 |
| **페이로드 (payload)** | 패킷의 내용물(실제 영상·음성). 암호화돼서 볼 수 없다 |
| **IP / IP 주소** | 인터넷의 집 주소 체계. IP 헤더에 보낸 곳·받는 곳 주소가 있다 |
| **포트 (port)** | 한 집(기기) 안의 방 번호. 어느 앱으로 갈 데이터인지 구분한다 |
| **TCP** | 도착 확인을 하는 꼼꼼한 전송 방식. 빠짐없이 가지만 느릴 수 있다(웹페이지, 파일) |
| **UDP** | 확인 없이 계속 보내는 빠른 방식. 일부가 사라져도 계속 간다. 영상통화가 주로 쓴다 |
| **RTP** | 영상·음성을 UDP로 보낼 때 붙이는 추가 송장(프레임 번호, 시각). "앱 계층" 정보라 vcaml의 핵심 방법은 이것 없이 IP/UDP 헤더만 쓴다. 카카오톡이 RTP를 쓰는지는 미확인 |
| **WebRTC** | 브라우저에서 영상통화를 하게 해 주는 기술. Meet가 사용한다 |
| **getStats / webrtc-internals** | WebRTC 통화 중 브라우저가 실제 fps·bitrate 등을 알려 주는 기능. 우리 **정답**의 출처 |
| **Wi-Fi 핫스팟** | 노트북이나 폰이 공유기 역할을 해서 다른 기기에 인터넷을 나눠 주는 것 |
| **RSSI** | Wi-Fi 신호 세기. 단위 dBm, 0에 가까울수록 강하다(−50은 강함, −80은 약함). [가정] −75 이하를 "약한 Wi-Fi" 기준 후보로 둔다 |
| **VPN** | 기기의 데이터를 특정 통로로 돌리는 기능. PCAPdroid는 이것을 이용해 폰 안에서 패킷을 기록한다. Android는 VPN을 한 번에 하나만 켤 수 있다 |

### 품질 관련
| 용어 | 쉬운 뜻 |
|---|---|
| **손실 (packet loss)** | 보낸 패킷 중 도착하지 못한 비율(%). 화면이 깨지거나 멈춘다 |
| **지연 (delay, latency)** | 데이터가 도착하기까지 걸리는 시간(ms). 대화가 엇갈린다 |
| **지터 (jitter)** | 지연이 들쭉날쭉한 정도. 화면이 버벅인다 |
| **대역폭 (bandwidth)** | 길의 넓이 = 1초에 보낼 수 있는 최대 양. 좁으면 앱이 화질을 낮춘다 |
| **처리량 (throughput)** | 실제로 1초에 보낸 양. 속도 측정(speedtest)으로 잰다 |
| **RTT** | 왕복 시간. 갔다가 돌아오는 데 걸린 시간. `ping`으로 잰다 |
| **QoE** | 사용자 체감 품질. 우리는 0–100 점수로 만든다 |
| **혼잡 제어** | 네트워크가 막히면 앱이 스스로 보내는 양을 줄이는 기능. What-if는 이것을 재현하지 못한다 |

### 단위
| 단위 | 뜻 | 감 잡기 |
|---|---|---|
| **ms** | 밀리초 = 1/1000초 | 100ms = 0.1초 |
| **bps / kbps / Mbps** | 초당 비트 / 천 비트 / 백만 비트 | 1 Mbps = 1000 kbps. 1 byte = 8 bit |
| **fps** | 초당 프레임(화면 장수) | 30 부드러움, 15 약간 끊김 |
| **px** | 픽셀 | 해상도 높이 720px = HD |
| **dBm** | 신호 세기 단위(음수) | −50 강함, −80 약함 |
| **B (byte)** | 바이트 | vcaml은 UDP 길이가 306바이트를 넘는 패킷을 "영상 패킷"으로 본다 |

### 머신러닝·평가
| 용어 | 쉬운 뜻 |
|---|---|
| **feature (특징)** | 모델에 넣는 입력값. 우리는 1초 동안의 패킷 크기 통계와 간격 통계 |
| **Random Forest** | 여러 개의 "질문 나무"(결정 트리)가 투표해서 답을 내는 모델. vcaml이 쓴다 |
| **학습 / 추론** | 학습 = 정답이 있는 데이터로 규칙 익히기. 추론 = 새 데이터에 규칙 적용하기 |
| **정답 (ground truth)** | 비교 기준이 되는 진짜 값. 우리는 getStats |
| **슬라이딩 윈도우** | 데이터를 1초씩 잘라 차례로 처리하는 것 |
| **k-fold 교차검증** | 데이터를 k(=5)등분해서 돌아가며 시험용으로 쓰는 공정한 평가법 |
| **MAE** | 평균 절대 오차. 작을수록 좋다. fps MAE 1.5 = 평균 1.5프레임 틀림 |
| **±2 fps 정확도** | 오차가 2fps 이내인 비율 |
| **Precision (정밀도)** | "저하"라고 판정한 것 중 진짜 저하인 비율. 헛경보가 적을수록 높다 |
| **Recall (재현율)** | 진짜 저하 중 "저하"라고 잡아낸 비율. 놓친 것이 적을수록 높다 |
| **F1** | Precision과 Recall의 조화 평균. 둘 다 좋아야 높다 |
| **Confusion Matrix (혼동 행렬)** | "정답 × 예측" 표. 무엇을 무엇으로 헷갈렸는지 보인다 |
| **일반화** | 학습한 환경(데스크톱)과 다른 환경(모바일)에서도 잘 맞는가 |
| **pickle (pkl)** | 학습된 모델을 저장한 파일 형식 |
| **MLflow** | 학습 실험 기록(설정, 오차, 모델 파일)을 관리하는 도구. vcaml이 쓴다 |

## 12. 교수님 면담 준비 (10/14 수 10:00)

### 12-1. 3분 설명 스크립트 (초안)
1. **문제 (30초)**: "영상통화 앱은 데이터를 암호화하기 때문에, 앱 밖에서는 통화 품질을 알기 어렵습니다. IMC 2023의 vcaml 연구는 패킷의 크기와 간격만으로 데스크톱 통화의 fps 등을 평균 1.5프레임 오차로 추정했습니다."
2. **우리 질문 (30초)**: "이것이 **모바일에서, 실시간으로도** 정확한지 검증하는 것이 목표입니다. 대상은 Galaxy S20의 Meet와 카카오톡입니다."
3. **방법 (60초)**: "폰의 PCAPdroid로 패킷을 노트북에 실시간으로 보내고, vcaml 모델로 1초마다 추정합니다. 결과는 웹 대시보드와 폰 위 오버레이 버블에 표시하고, 품질이 나쁘면 원인과 조치를 안내합니다. 이미 솔로 프로젝트에서 vcaml을 재현해 논문과 같은 수치(1.49 대 1.50)를 얻었습니다."
4. **검증 (40초)**: "캡처 충실도, Meet 정답과의 오차(MAE·F1), Clumsy로 주입한 손상을 라벨로 쓴 원인 진단 정확도, Meet와 카카오톡 비교, 이렇게 네 가지 실험을 합니다."
5. **일정·역할 (20초)**: "Sungmin이 ML 서버와 Flutter 앱, 팀원이 React 대시보드를 맡고, 11/24 기능 동결 후 12/2에 발표합니다."

### 12-2. 교수님께 여쭤볼 것 (후보)
1. vcaml 원본에 **라이선스 파일이 없습니다**. 수업 프로젝트에서 fork + submodule(코드 복사 없이 링크)로 쓰고 출처를 밝히는 방식이 괜찮은지.
2. 학교 Wi-Fi(igc_user)에서 **노트북 핫스팟 + Clumsy로 우리 폰 트래픽에만 손상을 넣는 실험**을 해도 되는지. 발표장에서 해도 되는지.
3. 범위가 적절한지: 핵심(정확도 검증) 대비 오버레이 앱·대시보드의 비중.
4. 평가에서 중요하게 보시는 것: 정확도 수치 vs 시스템 완성도 vs 발표.
5. 정답이 없는 카카오톡 결과를 "모델 추정값, 정성 비교"로만 제시해도 충분한지.
6. 최종 보고서의 형식과 마감(현재 [가정] 12/12).

### 12-3. 예상 질문과 답
| 질문 | 답 |
|---|---|
| vcaml과 무엇이 다른가? | 데스크톱·오프라인 → **모바일·실시간**. 정확도를 모바일에서 **다시 검증**하고, 원인 진단과 조치 안내를 더했다 |
| 카카오톡은 정답이 없는데 어떻게 평가하나? | 정량 평가는 정답이 있는 Meet로 한다. 카카오톡은 같은 조건에서 Meet와 비교하는 정성 평가이며, 화면에 항상 "추정값"으로 표시한다 |
| 왜 노트북 핫스팟인가? | 폰과 인터넷 사이에서 우리가 통제한 손상을 넣고, 동시에 노트북 쪽에서도 패킷을 기록해 캡처 정확도를 비교하기 위해서다 |
| 데모가 실패하면? | Replay 모드(녹화 재생)와 녹화본으로 즉시 전환한다 |
| 개인정보 문제는? | 우리 기기 트래픽만 기록하고, 내용은 암호화돼서 보지 않으며 크기와 시각만 쓴다 |
